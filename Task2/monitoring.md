# Внедрение мониторинга

Мониторинг - это систематический сбор, анализ и визуализация метрик, которые отражают состояние и производительность системы. Он состоит из трёх основных компонентов: сбор метрик (сборщики, агенты), хранение (временные ряды), визуализация и алертинг (дашборды, оповещения). Мониторинг позволяет обнаруживать проблемы до того, как они станут критическими, и принимать решения на основе данных, а не предположений.

## Мотивация

После открытия API для внешних компаний система «Александрита» столкнулась с рядом проблем, которые невозможно отследить с помощью Яндекс Метрики:

**Ключевые проблемы, которые решает мониторинг:**
1. **Потерянные заказы.** Клиенты и API-пользователи не получают заказы, жалобы растут. Заказы «зависают» на неопределённый срок. Без мониторинга проблема обнаруживается только через обращения клиентов - это означает, что реальное время реакции измеряется днями.
2. **Просроченные заказы.** После открытия API количество заказов выросло, а время их обработки увеличилось. Без метрик невозможно понять, на каком этапе заказ задерживается - в CRM, в MES или в очереди RabbitMQ.
3. **Медленная работа MES.** Операторы жалуются на загрузку первой страницы с дашбордом заказов. Это влияет на их продуктивность и вознаграждение, что в итоге сказывается на скорости обработки заказов.
4. **Потеря данных из Яндекс Метрики.** API-заказы от внешних компаний не попадают в воронку Яндекс Метрики. Руководство не видит полной картины нагрузки и конверсии.

**Что даст мониторинг:**
- Обнаружение проблем в течение минут, а не дней
- Возможность приоритизировать работы по реальной критичности
- Обоснование для расширения инфраструктуры с данными, а не с предположениями
- Понимание SLA/SLO для API-клиентов

## Выбор подхода к мониторингу

Для разных компонентов системы подходят разные методологии. Используем комбинированный подход.

### USE (Utilization, Saturation, Errors)

Применяется для инфраструктурных компонентов, где важно понимать потребление ресурсов:

- **RabbitMQ** - очередь сообщений между CRM и MES. Важно отслеживать количество сообщений в очередях, dead-letter-exchange, количество подключений.
- **PostgreSQL (Shop DB, MES DB)** - базы данных. Важно понимать количество активных соединений, утилизацию памяти, размер базы.
- **EC2 инстансы** - серверы, где работают API-сервисы. CPU, память, диск.

### RED (Rate, Errors, Duration)

Применяется для API-сервисов, где основной фокус на пользовательских запросах:

- **Shop API** - принимает заказы от B2C-клиентов.
- **CRM API** - управление заказами для менеджеров.
- **MES API** - расчёт стоимости, назначение заказов операторам. Также используется внешними API-клиентами.

### Four Golden Signals (Latency, Traffic, Errors, Saturation)

Применяется для пользовательских интерфейсов и критичных операций:
- **MES UI** (React) - операторы работают с дашбордом заказов, жалуются на скорость загрузки.
- **Процесс обработки заказа** - сквозная метрика от создания заказа до его закрытия.

## Метрики

### RabbitMQ

**Number of dead-letter-exchange letters in RabbitMQ**

Зачем нужна эта метрика: мёртвые письма (dead-letter) - это сообщения, которые не удалось обработать получателю. Их наличие означает, что заказы не доходят до адресата. Это критичная метрика для обнаружения потерянных заказов.
Лейблы метрики: `queue_name`, `exchange_name`, `environment`.

**Number of messages in flight in RabbitMQ**

Зачем нужна эта метрика: показывает количество необработанных сообщений в очереди. Если значение растёт, это означает, что получатели не справляются с нагрузкой или перестали обрабатывать сообщения.
Лейблы метрики: `queue_name`, `environment`.

### API-сервисы

**Number of requests (RPS) for API**

Зачем нужна эта метрика: показывает текущую нагрузку на API. Необходима для планирования ёмкости и обнаружения аномалий (всплесков или падений трафика).
Лейблы метрики: `service` (shop_api, crm_api, mes_api), `endpoint`, `method`, `environment`.

**Number of HTTP 500 for API**

Зачем нужна эта метрика: 5xx ошибки означают проблемы на стороне сервера. Их рост - индикатор деградации сервиса. Для API-клиентов SLA измеряется в проценте успешных ответов.
Лейблы метрики: `service`, `endpoint`, `environment`.

**Response time (latency) for API**

Зачем нужна эта метрика: задержка ответа напрямую влияет на пользовательский опыт и скорость обработки заказов. MES API используется для расчёта стоимости (2-30 минут), поэтому важно отслеживать не только медианную задержку, но и p95/p99.
Лейблы метрики: `service`, `endpoint`, `quantile` (p50, p95, p99), `environment`.

**Number of simultaneous sessions for API**

Зачем нужна эта метрика: количество активных соединений ограничено конфигурацией сервера. При приближении к лимиту новые запросы начинают отклоняться.
Лейблы метрики: `service`, `environment`.

**Kb transferred (received/sent) for API**

Зачем нужна эта метрика: позволяет оценить нагрузку на сеть и обнаружить аномалии (например, резкий рост исходящего трафика).
Лейблы метрики: `service`, `direction` (received/sent), `environment`.

### Базы данных (PostgreSQL)

**Memory Utilisation for DB instance**

Зачем нужна эта метрика: PostgreSQL использует память для буферов и кеша. При высокой утилизации запросы начинают выполняться медленнее из-за обращения к диску.
Лейблы метрики: `database` (shop_db, mes_db), `environment`.

**Number of connections for DB instance**

Зачем нужна эта метрика: PostgreSQL имеет ограниченное количество соединений (обычно 100-200). Если все соединения заняты, новые запросы ставятся в очередь или отклоняются.
Лейблы метрики: `database`, `environment`.

**Size of DB instance**

Зачем нужна эта метрика: размер базы данных растёт по мере накопления заказов. При достижении лимита хранилища возможны сбои записи.
Лейблы метрики: `database`, `environment`.

### Инфраструктура (EC2)

**CPU % for API service**

Зачем нужна эта метрика: высокая загрузка CPU (>80%) приводит к задержкам обработки запросов и увеличению времени отклика.
Лейблы метрики: `service`, `environment`.

**Memory Utilisation for API service**

Зачем нужна эта метрика: при нехватке памяти начинается swapping, что резко замедляет работу приложения.
Лейблы метрики: `service`, `environment`.

### Хранилище

**Size of S3 storage**

Зачем нужна эта метрика: 3D-файлы загружаются клиентами в S3, оттуда MES API забирает их для расчёта стоимости. Рост хранилища коррелирует с ростом количества заказов.
Лейблы метрики: `bucket_name`, `environment`.

### Бизнес-метрики (сквозные)

**Количество заказов по статусам**

Зачем нужна эта метрика: позволяет обнаружить заказы, которые «зависли» - долго находятся в одном статусе без перехода. Это ключевая метрика для решения проблемы потерянных заказов.
Лейблы метрики: `status`, `source` (B2C, API), `environment`.

**Время нахождения заказа в статусе**

Зачем нужна эта метрика: среднее время обработки заказа по статусам. Позволяет выявить узкие места. Например, если заказ в статусе PRICE_CALCULATED находится дольше обычного - проблема в MES API.
Лейблы метрики: `status`, `source`, `environment`.

**Количество заказов с просроченным сроком выполнения**

Зачем нужна эта метрика: прямо влияет на удовлетворённость клиентов и удержание контрактов. Заказы должны выполняться за 3 недели.
Лейблы метрики: `source`, `environment`.

## План внедрения

### Техническое задание

**Этап 1: Сборщик метрик**
- Установить Prometheus как централизованный сборщик метрик
- Развернуть node_exporter на EC2-инстансах для сбора метрик ОС (CPU, память, диск)
- Настроить exporters для существующих компонентов:
  - `postgresql_exporter` для Shop DB и MES DB
  - `rabbitmq_exporter` для RabbitMQ
- Для Spring Boot сервисов (Shop API, CRM API): добавить зависимость `micrometer-registry-prometheus`
- Для MES API (C#): интегрировать `prometheus-net`
- Добавить endpoint `/actuator/prometheus` (Shop API, CRM API) и аналогичный для MES API

**Этап 2: Визуализация**
- Развернуть Grafana
- Создать дашборды:
  - Обзорный дашборд для руководства (количество заказов, ошибки, latency)
  - Дашборд для Shop API (RPS, ошибки, latency по эндпоинтам)
  - Дашборд для CRM API
  - Дашборд для MES API (включая очередь сообщений и dead-letter)
  - Дашборд для RabbitMQ (очереди, DLX, подключения)
  - Дашборд для БД (соединения, память, размер)
- Настроить источник данных Prometheus в Grafana

**Этап 3: Алертинг**
- Настроить Alertmanager для отправки уведомлений (email, Telegram или Slack)
- Определить алерты:
  - Критичные (P1): 5xx ошибки > 1% за 5 минут, dead-letter messages > 0
  - Высокие (P2): CPU > 80%, память > 85%, latency p99 > 10 секунд
  - Предупреждающие (P3): количество заказов в статусе > 3 дней
- Настроить routing алертов по severity

**Этап 4: Бизнес-метрики**
- Добавить метрики заказов через actuator/поинт интеграции с БД
- Настроить дашборд для менеджеров (количество заказов по статусам, просроченные)
- Интегрировать с существующими уведомлениями (если есть)

### Ресурсы

- DevOps-инженер: настройка Prometheus, exporters, Grafana (основная нагрузка)
- Бэкенд-разработчики (Java, C#): добавление метрик в API-сервисы
- QA-инженер: верификация метрик после внедрения

### Критерии приёмки

- Prometheus собирает метрики со всех сервисов в течение 1 минуты
- Grafana отображает данные с задержкой не более 30 секунд
- Все критичные алерты срабатывают в течение 5 минут при наступлении условия
- Дашборды доступны и читаемы для тимлида и продакт-менеджера
