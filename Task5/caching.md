# Архитектурное решение по кешированию

## Мотивация

### Проблемы, которые решает кеширование

1. **Низкая скорость работы операторов MES** - первая страница с дашбордом заказов грузится медленно, что напрямую влияет на продуктивность сотрудников и их вознаграждение (кто взял заказ - тот получает оплату).
2. **Задержки в обслуживании B2C и B2B клиентов** - клиенты видят устаревшие статусы заказов, что приводит к жалобам и потере контрактов.
3. **Нагрузка на базу данных** - рост количства заказов (100 в месяц) увеличивает количество запросов на чтение списков заказов.

### Какие элементы системы планируются к кешированию

- Дашборд MES: список заказов в работе с фильтром по статусам
- Метаданные заказов (базовая информация: ID, статус, дата создания, клиент)

## Предлагаемое решение

### Тип кеширования: серверное

Обоснование выбора:
- Клиентское кеширование (браузер) не подходит, так как операторы работают с одного рабочего места, данные должны быть актуальными для всех
- Серверное кеширование позволяет централизованно управлять кешем и обеспечивать консистентность данных между всеми пользователями MES
- MES является единственным источником данных о статусах заказов для операторов

### Паттерн кеширования: Cache-Aside

#### Описание паттерна

Cache-Aside работает следующим образом:
1. При запросе данных приложение сначала проверяет кеш
2. Если данные есть в кеше (cache hit) - возвращаются клиенту
3. Если данных нет (cache miss) - запрос идет к базе данных
4. Результат сохраняется в кеш и возвращается клиенту

#### Почему Cache-Aside подходит для MES

| Паттерн | Подходит | Обоснование |
|---------|----------|-------------|
| Cache-Aside | ✓ | MES является владельцем данных, записи поступают через RabbitMQ. Паттерн прост в реализации и не требует тесной связки с источником данных. |
| Write-Through | ✗ | При каждом изменении статуса потребуется двойная запись (БД + кеш), что увеличит задержку. Для высоконагруженной системы записи это избыточно. |
| Refresh-Ahead | ✗ | Сложный в реализации, требует предсказания паттернов доступа. Обновление может быть ресурсоёмким, особенно с учетом неравномерной нагрузки. |

### Сущности для кеширования

| Сущность | Ключ кеша | TTL |
|----------|----------|-----|
| Список заказов по статусу | `orders:status:{status}:page:{page}` | 60 сек |
| Метаданные заказа | `order:{orderId}:meta` | 300 сек |
| Количество заказов по статусу | `orders:count:{status}` | 60 сек |

### Стратегия инвалидации кеша

#### Сравнительная таблица стратегий

| Стратегия | Описание | Плюсы | Минусы | Вердикт |
|-----------|----------|-------|--------|---------|
| Временная (TTL) | Данные удаляются через заданное время | Простая реализация, не требует интеграций | Вероятность получения устаревших данных | Резервная стратегия |
| По ключу (event-driven) | Инвалидация по событию при изменении данных | Точная инвалидация, минимум устаревших данных | Требует интеграции с RabbitMQ | Основная стратегия |
| Программная (manual) | Ручная инвалидация по API | Полный контроль | Сложность поддержки, риск человеческой ошибки | Резервная стратегия |

#### Окончательный выбор: Event-driven инвалидация + TTL как fallback

Обоснование:
- MES получает обновления статусов через RabbitMQ-сообщения
- При получении сообщения об изменении статуса заказа MES инвалидирует соответствующие ключи кеша
- TTL служит защитой от устаревших данных на случай, если сообщение будет потеряно

**Процесс инвалидации:**
1. MES получает сообщение `ORDER_STATUS_CHANGED` из очереди
2. MES определяет, какие ключи кеша затронуты (по orderId, старому и новому статусу)
3. MES удаляет соответствующие ключи из Redis
4. Следующий запрос к дашборду получит актуальные данные из БД

## Резюме решения

- **Тип кеширования:** серверное (MES)
- **Паттерн:** Cache-Aside
- **Хранилище:** Redis
- **Инвалидация:** event-driven (через RabbitMQ) + TTL 60 сек
- **Что кешировать:** списки заказов по статусам, метаданные заказов, счетчики

Данное решение обеспечит:
- Уменьшение времени загрузки дашборда MES (снижение нагрузки на БД)
- Актуальность данных для операторов (инвалидация при изменении статусов)
- Масштабируемость системы при росте количества заказов
